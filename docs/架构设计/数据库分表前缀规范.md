# 数据库分表前缀规范

> 版本：v1.0.0
> 适用范围：五常同城全平台（12 中台 + 15 垂直业务）
> 依据：`docs/架构设计/ershou-大模块架构方案.md`（v3.2.1）第 6.5 节 分表前缀规范
> 维护：Agent 2 数据库
> 创建时间：2026-07-19

---

## 一、设计目标

1. **模块隔离**：每个中台 / 垂直业务在数据库层通过表名前缀清晰隔离，避免跨模块误操作。
2. **演进友好**：表名前缀即模块标识，便于后期按模块拆分独立 Schema 或独立数据库。
3. **统一规范**：所有业务表必须归属某个前缀域，禁止裸表名（如 `users`、`orders`）。
4. **索引/字段规范**：主键、时间字段、软删除字段全平台统一，便于 ORM 与监控治理。

---

## 二、表名命名规则

### 2.1 总规则

```
{前缀}_{业务表名}
```

- 前缀：小写字母 + 下划线，固定对应一个模块（中台或垂直业务）
- 业务表名：小写字母 + 下划线，单数形式，语义化命名
- 全表名：全小写，单词间用下划线分隔（snake_case）
- 示例：`ers_listings`、`pay_orders`、`user_profiles`、`lbs_pois`

### 2.2 命名禁忌

| 反例 | 正例 | 说明 |
|------|------|------|
| `users` | `user_profiles` | 缺少模块前缀 |
| `UserProfiles` | `user_profiles` | 大小写混用 |
| `user_profile` | `user_profiles` | 单数形式 |
| `usr_profiles` | `user_profiles` | 缩写不直观 |
| `user_user_profiles` | `user_profiles` | 前缀重复 |

## 五、通用字段与索引规范

### 5.1 通用字段（所有业务表必须包含）

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| `id` | `BIGSERIAL` | `PRIMARY KEY` | 主键，统一 BIGSERIAL（8 字节自增） |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | 创建时间，带时区 |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | 更新时间，带时区，由触发器自动维护 |
| `deleted_at` | `TIMESTAMPTZ` | `NULL`（软删除） | 软删除时间，GORM DeletedAt 默认实现 |

> **注意**：业务表如需地区隔离，应新增 `region_id BIGINT NOT NULL` 字段并建索引，参考 `database.RegionBaseModel`。

### 5.2 主键规范

- **统一 `BIGSERIAL`**：8 字节自增整型，预留足够空间避免溢出
- **禁止 UUID 主键**：UUID 索引性能差，如需对外暴露 ID 使用 `BIGSERIAL` 主键 + 独立的 `uuid` 字段（带索引）
- **禁止复合主键**：用唯一约束替代，主键始终为单列 `id`

### 5.3 时间字段规范

- **统一 `TIMESTAMPTZ`**：带时区的时间戳，避免跨时区问题
- **禁止 `TIMESTAMP`（无时区）**：会引发时区歧义
- **禁止 `DATE`/`TIME` 单独使用**：业务表统一使用 `TIMESTAMPTZ` 完整时间戳
- **默认值统一 `NOW()`**：数据库层保证，不依赖应用层

### 5.4 索引规范

| 索引类型 | 使用场景 | 示例 |
|---------|---------|------|
| B-Tree（默认） | 等值查询、范围查询、排序 | `CREATE INDEX idx_xxx ON tbl(col)` |
| GIST | 地理字段（PostGIS） | `CREATE INDEX idx_xxx_geom ON tbl USING GIST(geom)` |
| GIN | JSONB、数组、全文检索 | `CREATE INDEX idx_xxx_payload ON tbl USING GIN(payload)` |
| 部分索引（WHERE） | 仅索引满足条件的行 | `CREATE INDEX idx_xxx ON tbl(col) WHERE enabled = TRUE` |

**索引命名规则**：`idx_{表名缩写}_{字段名}`，例如 `idx_listings_status`、`idx_orders_user_id`。

**强制索引场景**：
1. 所有外键字段必须建索引
2. 所有 `WHERE` 高频过滤字段必须建索引（如 `status`、`enabled`、`region_id`）
3. 所有 `ORDER BY` 字段必须建索引（如 `created_at`、`sort`）
4. JSONB 字段如需查询内部 key，使用 GIN 索引

### 5.5 软删除规范

- 使用 `deleted_at TIMESTAMPTZ NULL` 实现软删除
- GORM 默认支持，查询自动过滤 `deleted_at IS NULL`
- 唯一约束需配合软删除：`UNIQUE(col, deleted_at)` 或部分唯一索引 `WHERE deleted_at IS NULL`

## 六、分库分表演进路径

### 6.1 阶段一：单库起步（P0 - 当前）

```
┌─────────────────────────────────────────┐
│  wuchang_tongcheng（单库）              │
│  ├── modules / cron_jobs / ...          │  ← 6 张核心表
│  ├── user_profiles / user_sessions      │  ← 12 中台前缀表
│  ├── ers_listings / ers_trades          │  ← 15 垂直业务前缀表
│  └── ...                                │
└─────────────────────────────────────────┘
```

- 所有表共存于 `wuchang_tongcheng` 单库
- 通过表名前缀实现逻辑隔离
- 适用：日活 < 10 万，单表数据量 < 1000 万

### 6.2 阶段二：单库分表（P2 - 按需）

```
┌─────────────────────────────────────────┐
│  wuchang_tongcheng（单库）              │
│  ├── ers_listings_0 ~ ers_listings_15   │  ← 按用户 ID 取模分 16 表
│  ├── pay_orders_0 ~ pay_orders_15       │
│  └── ...                                │
└─────────────────────────────────────────┘
```

- 单表数据量超 1000 万后按前缀域水平拆分
- 分表键：用户 ID / 订单 ID 取模
- 分表数：16 / 64 / 256（2 的幂次）
- 适用：日活 10 万 - 100 万，单前缀域数据量 > 1000 万

### 6.3 阶段三：按模块独立 Schema（P3 - 按需）

```
┌─────────────────────────────────────────┐
│  wuchang_tongcheng（实例）              │
│  ├── schema_user  (user_* 全部表)       │
│  ├── schema_pay   (pay_*  全部表)       │
│  ├── schema_ers   (ers_*  全部表)       │
│  └── ...                                │
└─────────────────────────────────────────┘
```

- 每个模块独立 Schema，权限隔离
- 表名去除前缀：`schema_user.profiles`、`schema_pay.orders`
- 跨 Schema 查询使用 `schema.table` 限定
- 适用：日活 100 万+，模块间 IO 争抢明显

### 6.4 阶段四：按模块独立数据库（P4 - 终态）

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  db_user     │  │  db_pay      │  │  db_ers      │
│  user_*      │  │  pay_*       │  │  ers_*       │
└──────────────┘  └──────────────┘  └──────────────┘
       │                │                │
       └────────────────┴────────────────┘
                        │
              ┌─────────────────┐
              │  跨库事务 / 消息  │
              │  最终一致性       │
              └─────────────────┘
```

- 每个模块独立数据库实例，物理隔离
- 跨库事务通过 `message_queue` 本地消息表 + 最终一致性保证
- 适用：日活 500 万+，单库无法承载

### 6.5 演进原则

1. **前缀即模块边界**：表名前缀是模块的唯一标识，演进时按前缀整体迁移
2. **渐进式拆分**：每阶段独立验证，避免一次性大重构
3. **应用无感**：通过 ORM 抽象层屏蔽底层拆分，应用代码不变
4. **数据先行**：拆分前先做数据冷热分离、归档，降低迁移量

## 七、迁移工具与种子数据

### 7.1 自动迁移工具

```
go run ./cmd/migrate up          # 执行所有正向迁移
go run ./cmd/migrate down        # 执行所有回滚迁移
go run ./cmd/migrate status      # 查看迁移状态
go run ./cmd/migrate up --module=ershou  # 按模块独立迁移（预留）
```

迁移脚本存放：`backend/migrations/*.sql`
- 正向迁移：`{序号}_{名称}.sql`（如 `001_p0_baseline.sql`）
- 回滚迁移：`{序号}_{名称}_rollback.sql`（如 `002_p0_rollback.sql`）
- 状态记录：`schema_migrations` 表

### 7.2 种子数据

种子文件：`backend/internal/pkg/seed/seed.go`
- `SeedModules()`：注册 12 中台 + 15 垂直业务到 `modules` 表
- `SeedCronJobs()`：注册 P0 阶段定时任务到 `cron_jobs` 表
- 由 `seed.Run()` 统一调用，幂等执行
