## 一、开发目标

依据 v3.2.1 架构方案第二章 2.2.A 节 + 用户要求"对标各大平台、超前行、想全面"，**一次性开发 ershou 二手交易模块完整功能**，作为后续 14 个垂直模块（job/house/car/love 等）的开发样板。

**对标平台**：
- 闲鱼（C2C 闲置交易 + 拍卖 + 社区）
- 转转（C2C + B2C 二手 + 质检鉴定）
- 58 同城（分类信息 + 同城交易）
- 瓜子二手车（车况检测 + 担保交易）
- 贝壳租房（真房源 + 担保交易）
- 趣店（分期付款 + 金融）

**核心交付**：
1. 数据库扩展：新增 15+ 张子表（SKU/订单/拍卖/付费推广/举报/评价/商家店铺/物流/担保交易/标签/品牌/型号等）
2. 后端完整开发：60+ API（商品发布增强 + 交易流程闭环 + 营销推广 + 风控审核 + IM + 数据统计 + 商家店铺 + 标签分类 + 搜索推荐）
3. 前端管理后台：15+ 页面（运营管理 + 商家管理 + 风控中心 + 数据中心）
4. 前端 C 端：发布/详情/列表/搜索/订单/拍卖/收藏/关注/消息
5. 依赖 P1 中台精简版：pay 担保交易 / im 聊天 / material 以图搜图 / risk 举报 / ai 审核

### 关键技术决策

| 决策点 | 方案 | 原因 |
|--------|------|------|
| Handler 模式 | 每个 Handler 文件定义独立 Handler 结构体 + 构造函数注入 Service | 与现有 ershou.go 的 Handler 模式保持一致，便于维护 |
| 聚合 Handler | TradeHandler/RiskHandler/CatalogHandler 聚合多个 Service | 避免文件过多，将业务相关的 Service 聚合到同一 Handler |
| URL 参数解析 | 新增 `parseSubID(ctx, key)` 辅助函数解析 `:sku_id`/`:order_id` 等自定义子参数 | 区分于 `:id`（ershous 主表 ID），避免语义混淆 |
| 订单状态机 | 11 状态（pending/paid/shipped/delivered/received/completed/canceled/refunding/refunded/dispute/dispute_closed/closed） | 对标闲鱼/转转，覆盖完整交易闭环 + 售后 |
| 拍卖自动延拍 | 截拍前 5 分钟内出价，自动延 5 分钟 | 对标闲鱼，防止最后一秒抢单 |
| 担保 T+1 放款 | Release 方法将 frozen/released 状态推到 paid | T+1 自动放款由调度任务实现，与 Release 解耦 |
| 退款状态机 | 10 状态（pending→reviewing→approved→rejected→refunding→refunded→closed/dispute/dispute_closed/canceled） | 对标转转，覆盖退货/换货/纠纷 |
