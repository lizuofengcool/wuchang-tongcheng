## 一、开发目标

依据 `docs/架构设计/ershou-大模块架构方案.md`（v3.2.1）第十二章 P0 阶段规划，完成全平台底层基座 + 模块插件抽象层，为 P1 12 大通用中台开发提供基础。

**核心交付**：
1. Go 模块化插件底层框架（统一 Plugin 接口 + Meta() 方法 + 模块开关 + 动态注册 + 独立路由）
2. modules 模块注册表 + cron_jobs 调度中心 + module_grayscales 灰度发布表
3. message_queue 本地消息表 + 对账任务基础框架
4. module_station_configs 分站配置中心扩展
5. Prometheus + Grafana 监控基座接入
6. 数据库分表前缀规范 + 自动迁移工具 + PostGIS 地理索引
7. 基础用户/地区/文件/权限通用底座（复用现有）
8. 4 端管理后台「模块总控面板」基础页面

**6 张核心表**（依据架构方案附录 A.1）：
1. `modules` - 模块注册表（name/display_name/category/version/enabled/dependencies）
2. `cron_jobs` - 定时任务调度中心（module_name/job_name/cron_expr/handler/enabled）
3. `module_grayscales` - 灰度发布表（module_name/version/gray_type/gray_config/status）
4. `message_queue` - 本地消息表（biz_module/biz_id/message_type/payload/status/retry_count）
5. `module_station_configs` - 分站配置中心扩展（station_id/module_name/config_key/config_value）
6. `module_metrics` - 监控指标表（module_name/metric_name/metric_value/labels/recorded_at）

1. **monitoring 目录路径与 docker-compose 相对路径问题**
   - 问题：任务要求 monitoring 文件位于项目根目录 `monitoring/`，但 `deploy/docker-compose.yml` 中 `./xxx` 相对路径默认解析为 `deploy/xxx`（参考现有 `./initdb` → `deploy/initdb/`）
   - 解决：compose 挂载路径使用 `../monitoring/...`（如 `../monitoring/prometheus.yml`），使其正确解析到项目根目录的 monitoring 文件夹
   - 验证：`docker-compose config` 通过，运行时可正确挂载

2. **backend/configs/config.example.yaml 与现有 config.yaml.example 命名差异**
   - 问题：任务要求新建 `config.example.yaml`，但项目已存在 `config.yaml.example`（完整版，含 STS/OAuth 等高级配置）
   - 解决：按任务要求创建 `config.example.yaml`（P0 精简模板），在文件头注明与完整版的关系，两者共存不冲突

3. **应用服务（backend/admin/pc）默认启动策略**
   - 问题：backend/admin/pc 需要构建镜像，开发环境频繁启动会影响效率
   - 解决：为这三个服务添加 `profiles: app`，默认不启动，需 `--profile app` 显式启动；监控类服务（prometheus/grafana/node-exporter/postgres-exporter/redis-exporter）默认启动；rabbitmq-exporter 使用 `profiles: monitoring`

4. **docker-compose.yml version 属性过时警告**
   - 问题：`docker-compose config` 输出 `version` 属性过时警告
   - 解决：保留现有 `version: '3.8'` 不动（属于现有文件，遵循"保留现有服务不动"约束），警告不影响功能

### Agent 2（数据库）遇到的问题

1. **PowerShell 不支持 `&&` 语句分隔符**
   - 问题：在 Windows PowerShell 中执行 `cd backend && go build` 报错 `The token '&&' is not a valid statement separator`
   - 解决：使用 RunCommand 工具的 `cwd` 参数指定工作目录，避免 `cd` 链式命令；或使用 `;` 替代 `&&`

2. **map 类型不能直接作为 if 条件**
   - 问题：migrate 工具中 `if applied[m.Filename]` 编译报错 `non-boolean condition in if statement`，因为 `applied` 是 `map[string]time.Time`，取值返回 `time.Time` 而非 `bool`
   - 解决：改用 comma-ok 模式 `if _, ok := applied[m.Filename]; ok`

3. **`go build ./...` 失败于 Agent 1 的文件**
   - 问题：`go build ./...` 报错 `internal/core/middleware/module_check.go:71: syntax error: unexpected EOF` 和 `cmd/server/main.go:199: RegisterAllRoutes 参数不匹配`
   - 原因：Agent 1 已修改 `plugin.RegisterAllRoutes` 签名（新增 `*gorm.DB` 参数用于模块开关查询），但尚未同步更新 `cmd/server/main.go` 和 `module_check.go`（语法不完整）
   - 解决：不属于 Agent 2 范围，已通过单独编译 `./internal/pkg/seed/` 和 `./cmd/migrate/` 验证本 Agent 产出无误，待 Agent 1 完成同步修复后 `go build ./...` 即可通过

4. **种子函数使用 raw SQL 而非 GORM Model**
   - 问题：modules / cron_jobs 表由 SQL 迁移脚本创建（非 GORM AutoMigrate），seed 包中没有对应 GORM Model
   - 解决：种子函数使用 `db.Exec()` + `INSERT ... ON CONFLICT ... DO UPDATE` 原生 SQL，避免创建 Model 文件（属于 Agent 1 的 module 模块范围），同时保证幂等性

### Agent 1（后端架构）遇到的问题

1. **service.go 中 database 包未使用导致编译失败**
   - 问题：初始版本 import 了 `database` 包并写了 `var _ = database.GetDB` 占位，但实际未使用，Go 编译报 `imported and not used`
   - 解决：移除 `database` 包 import 和 `var _ = database.GetDB` 行（service 层通过依赖注入接收 db，不直接调用 database.GetDB）

2. **module/plugin.go 中 logger.Warn 调用方式错误**
   - 问题：使用 `logger.Warn("xxx", "error", err)` 这是 sugared logger 的 key-value 风格，但 `logger.Warn` 接受的是 `zap.Field`，编译报类型不匹配
   - 解决：import `go.uber.org/zap`，改为 `logger.Warn("xxx", zap.Error(err))`

3. **module_check.go 中间件初次实现复杂度过高**
   - 问题：第一版使用字符串 "0"/"1" 标记缓存，但禁用模块需要查 DB 获取 DisplayName，逻辑复杂且不易维护
   - 解决：重写为使用 `redispkg.GetJSON/SetJSON` 缓存完整 `moduleStatus` 结构体（含 DisplayName 和 Enabled），简化逻辑

4. **避免循环依赖**
   - 问题：`module_check.go` 中间件需要查询 modules 表，若直接依赖 `module` 包会造成循环依赖（module 包的 plugin.go 调用 middleware）
   - 解决：`module_check.go` 中自定义最小 `moduleStatus` 结构体（仅 DisplayName + Enabled 两个字段），使用 `db.Table("modules").Select(...)` 原生查询，不依赖 module 包

5. **modules 表同步时机**
   - 问题：`SyncAllFromManager` 需要所有插件已注册到 Manager 才能同步，但 Go init 顺序不确定
   - 解决：在 `module` 包的 `Init()` 中调用 `SyncAllFromManager`（Init 在所有插件 init 注册完成后由 `pluginManager.InitAll(ctx)` 统一调用），`modules.go` 中将 `_ "wuchang-tongcheng/internal/modules/module"` 导入放在最后作为编码规范保险

6. **Gin 路由树不支持运行时删除**
   - 问题：任务 1.4 要求实现 `UnregisterRoutesFor(name)` 方法，但 Gin 路由树不支持运行时删除已注册的路由
   - 解决：`UnregisterRoutesFor(name)` 返回 nil（no-op），实际拦截由 `ModuleCheck` 中间件完成（禁用模块的请求在中间件层直接返回 403，不会进入业务 handler）
